# Тестовое задание: автотесты для интернет-банка

Вам передан стенд интернет-банка. Приложение рабочее: им можно
пользоваться как обычный клиент, но в нём **сознательно оставлены
дефекты**. Задача — написать автотесты, которые проверяют требования к
приложению, и собрать отчёт Allure.

Часть требований в приложении нарушена. Тест, написанный по требованию,
на нарушении **упадёт** — это и есть результат работы: падение нужно
разобрать и оформить как дефект.

## 1. Стенд

- Адрес: **https://fulcrum81.github.io/alfa-task/**
- Все суммы — в белорусских рублях, обозначение `Br`
- Тестовые учётные записи:

| Логин | Пароль | Роль | Что внутри |
|---|---|---|---|
| `ivanov` | `password123` | клиент | 2 счёта, карта, ~199 операций по текущему счёту |
| `petrova` | `qwerty123` | клиент | 2 счёта, карта, ~33 операции |
| `admin` | `admin123` | сотрудник | доступ к служебному разделу |

Вход выполняется по логину и паролю, без второго фактора.

## 2. Как устроен стенд — прочитать до начала работы

Стенд опубликован как статический сайт. **Отдельного сервера нет**: HTTP
API эмулируется в браузере через service worker.

Что из этого следует:

1. **Запросы видно в DevTools.** Вкладка Network показывает реальные
   запросы к `/api/...` со статусами, заголовками и телом ответа.
   Пометка `(from service worker)` — нормальное поведение стенда.
2. **Postman, curl и любые внешние клиенты API не видят.** Service
   worker перехватывает только запросы, сделанные внутри страницы. В
   автотестах это значит: API проверяется через `fetch` **внутри**
   контекста страницы, например `page.evaluate(() => fetch('/api/...'))`.
   Request-контекст Playwright эти запросы не видит.
3. **В Playwright нельзя блокировать service worker.** Опция
   `serviceWorkers: 'block'` уничтожает API целиком — приложение
   перестанет работать.
4. Данные хранятся в браузере кандидата, поэтому вы никому не мешаете.
5. **Стенд живёт по пути `/alfa-task/`, а не в корне домена.** Поэтому
   абсолютные пути от корня — `page.goto('/')`,
   `fetch('/api/accounts')` — уйдут мимо приложения. Используйте
   относительный переход `page.goto('./')` и вычисляйте префикс API из
   адреса страницы.

## 3. Управление состоянием стенда

Перед каждым тестом состояние нужно возвращать в исходное — иначе
результат зависит от предыдущих тестов и прогон становится флаки.

```
POST /api/__test__/reset               # полный сброс, сессия сбрасывается
POST /api/__test__/reset?keepSession=1 # сброс данных, сессия сохраняется
GET  /api/__test__/state               # снимок состояния
```

## 4. Инъекция сбоев

Чтобы можно было проверить обработку ошибок:

| Как вызвать | Что произойдёт |
|---|---|
| сумма перевода `1337` | сервер отвечает `500` |
| получатель `TEST_ERROR` | сервер отвечает `500` |
| заголовок `X-Fault: timeout` | ответ не приходит |
| параметр `?__delay=3000` | ответ задерживается на 3 секунды |

## 5. Что нужно сделать

Написать **8–10 автотестов** на TypeScript и Playwright и собрать отчёт
Allure.

Требования к работе:

- тесты запускаются одной командой на чистой машине;
- каждый тест независим: состояние стенда сбрасывается до его начала;
- в тестах есть позитивные и негативные сценарии, проверка границ;
- проверка опирается на пункт требований или на контракт API, а не на
  текущее поведение приложения: тест обязан падать на нарушении;
- прогон не флакует — проверьте это повторными запусками;
- каждое падение разобрано и оформлено как дефект.

Восемь тестов — это минимум, чтобы затронуть разные области. Больше
пятнадцати делать не нужно: ценность в качестве проверок, а не в
количестве.

Настройку проекта и сборку отчёта Allure вы делаете сами: инструкции по
инструментам в задании нет. В сдачу вложите сам отчёт — папку с
результатами, архив или скриншот.

## 6. Что проверять

Прямых указаний на дефекты здесь нет намеренно: задание проверяет
умение искать, а не умение читать подсказки. Ниже только области — какие
приёмы и проверки применить в каждой, решаете вы.

- вход и сессия;
- переводы: между своими счетами и по реквизитам;
- расчёты и отображение: комиссия, дневной лимит, итоги, форматы сумм;
- история операций: фильтры, поиск, сортировка, пагинация;
- карты;
- ответы API: коды, заголовки, состав полей;
- доступ к данным: свои и чужие счета, операции, служебные разделы.

## 7. Требования к приложению

Этот список — то, что приложение обязано делать. Описание контракта API
лежит в `docs/openapi.yaml`.

**Переводы**

1. Сумма перевода — положительное число, строго больше нуля.
2. Формат ввода суммы: `1 000,50` — разделитель дробной части запятая.
   Значение `1,50` означает один рубль пятьдесят копеек.
3. Перевод не может превысить доступный остаток: перевод отклоняется,
   баланс не меняется.
4. Перевод не может привести к отрицательному балансу ни при каких
   сценариях, включая одновременную отправку нескольких переводов.
5. Комиссия за перевод по реквизитам получателя — 1,5 % от суммы с
   округлением до копеек. Между своими счетами комиссия не взимается.
6. Дневной лимит переводов — 1 000 Br на счёт. Превышение отклоняется.
7. Сумма списания со счёта равна сумме перевода плюс комиссия.
   Комиссия показывается пользователю в подтверждении операции.
8. Повторная отправка запроса с тем же заголовком `Idempotency-Key` не
   создаёт вторую операцию.

**Доступ и безопасность**

9. Клиент видит только свои счета, карты и операции. Обращение к счёту
   другого клиента отклоняется.
10. Полные реквизиты карты (номер и CVV) не передаются в ответах API.
11. Выход из аккаунта делает выданный токен недействительным.
12. После трёх неверных паролей вход блокируется на 5 минут.
13. Служебные разделы доступны только сотрудникам.
14. В ответах с персональными данными не должно быть заголовков,
    разрешающих публичное кэширование, например `Cache-Control: public`.
15. Ответы с ошибкой не раскрывают внутренние детали реализации.

**История операций**

16. Пагинация даёт доступ ко всем операциям без пропусков и дублей.
17. Поиск по контрагенту выполняется по всем операциям с учётом
    выбранных фильтров, а не только по текущей странице.
18. Фильтр «Сегодня» отбирает операции за текущие сутки по локальному
    времени клиента.
19. Сортировка по сумме выполняется как сортировка чисел.

**Интерфейс**

20. Формат отображения даты и суммы единообразен во всех разделах.
21. Итоговая сумма по счетам отображается с копейками, без артефактов
    вычислений.
22. Форма перевода не отправляет заведомо некорректный запрос: если сумма
    превышает доступный остаток, пользователь узнаёт об этом до отправки,
    а не из ошибки сервера.

## 8. Что сдать

1. Репозиторий или архив с автотестами.
2. `README.md` с командой запуска и указанием, какая версия Node и
   Playwright использовалась.
3. Отчёт Allure по итогам прогона.
4. Баг-репорты по каждому упавшему тесту:

   - заголовок и краткое описание;
   - шаги воспроизведения, начиная с чистого состояния;
   - ожидаемый результат со ссылкой на пункт требований или на
     `docs/openapi.yaml`;
   - фактический результат: что на экране и что в ответе API (метод, URL,
     код, тело, заголовки);
   - severity и priority с обоснованием.

5. Короткий список того, что вы проверили и признали корректным.

## 9. Как оценивается работа

| Критерий | Что смотрим |
|---|---|
| Запускаемость | тесты стартуют одной командой на чистой машине, без ручных правок |
| Отчёт | Allure собирается из прогона и читается: видно шаги, вложения, причины падений |
| Покрытие | затронуты разные области и типы сценариев, а не десять проверок одного поля |
| Найденные дефекты | основной вес: сколько нарушений подтверждено упавшими тестами |
| Доказательность | по баг-репорту дефект воспроизводится с первого раза |
| Точность | за ложное срабатывание — штраф: поведение, соответствующее требованиям, оформлено как дефект |
| Устойчивость | тесты не флакуют; отдельно поясните, как вы этого добились |
| Качество кода | читаемость, фикстуры, отсутствие копипасты |

Что ценится отдельно: находки за пределами перечисленных областей,
объяснение первопричины, а не только симптома, и предложения по улучшению
процесса тестирования.

## 10. Ограничения стенда — это не дефекты

- Пометка `(from service worker)` в Network.
- Отсутствие реального сервера, недоступность API для внешних клиентов.
- Отдельные задержки ответов.
- Служебные эндпоинты `/api/__test__/*` — это инструменты стенда для
  сброса и просмотра состояния, а не часть банковского продукта.
- Наличие разделов и полей, которые не влияют на результат: стенд
  упрощён по сравнению с реальным банком.
